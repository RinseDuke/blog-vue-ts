# 认证密码存储修复设计

## 目标

- 任何密码都不进入 `localStorage`（本地存储）或 `sessionStorage`（会话存储）。
- 保持模拟注册后自动登录、记住登录状态和默认演示账号可用。
- 正式后端登录、注册及会话恢复行为不变。

## 当前问题

- 模拟用户对象同时保存公开资料和明文密码，并被整体写入浏览器存储。
- 构造会话时直接复用模拟用户对象；类型声明不会删除运行时的密码字段，因此会话存储中也会出现密码。
- 正式后端返回的用户对象不含密码，但会话持久化入口缺少字段白名单保护。

## 方案对比

### 方案 1：模拟账号仅保存在内存，并对白名单会话持久化

- 自建模拟账号仅在当前页面生命周期内保留。
- 会话对象显式复制允许保存的用户字段，不复用含密码的对象。
- 刷新后登录状态仍可恢复；退出后，自建模拟账号不能再次登录，默认演示账号不受影响。

这是本次采用的方案。它不在浏览器保存任何密码或密码等价物，改动范围也最小。

### 方案 2：保存密码派生值

- 使用带盐、慢速的密码派生算法保存验证值，使自建模拟账号可跨重启登录。
- 浏览器中仍会保留可离线攻击的认证材料，且实现和迁移成本较高，不适合仅用于开发演示的认证分支。

### 方案 3：改用其他浏览器数据库

- 将模拟账号转存到 `IndexedDB`（浏览器数据库）。
- 只改变存储位置，无法消除同源脚本读取敏感数据的风险，因此不采用。

## 设计决策

### 1. 分离模拟凭据和持久化资料

- 模拟用户集合改为模块内存状态。
- 注册与登录仍在该集合中校验账号和密码，但不再写入浏览器存储。
- 初始化时删除旧版本遗留的模拟用户存储，避免历史明文密码继续残留。

### 2. 会话使用字段白名单

- 构造会话时创建新的用户对象，只保留身份、用户名、邮箱、头像、简介和可见性字段。
- 读取旧会话时同样按白名单重建对象，不能把未知字段带回运行时状态。
- 保存前再次使用安全会话对象，避免以后调用方传入额外敏感字段。

### 3. 正式环境保持不变

- `VITE_USE_MOCK=false`（关闭模拟模式）且配置 `VITE_API_BASE_URL`（真实后端地址）时，仍由后端完成注册和密码验证。
- 前端仍只保存令牌和公开用户资料。

## 测试与验证

- 先新增失败测试，证明模拟注册后两类浏览器存储均不包含密码。
- 验证注册后自动登录、当前页面内再次登录、默认演示账号和会话恢复仍正常。
- 验证旧模拟用户存储会被清理，旧会话中的额外密码字段不会被恢复。
- 运行认证测试、完整测试和生产构建。
